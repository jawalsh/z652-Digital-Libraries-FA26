# Week 7: Metadata Studio / MAP Workshop / Project Consultation

## Summary

This week is a working studio devoted to the **Metadata Application Profile (MAP)** for your final project. Weeks 5 and 6 introduced the concepts needed to design a MAP: elements and values, Dublin Core, obligation, cardinality, controlled vocabularies, encoding schemes/value standards, content guidelines, and CollectionBuilder-specific metadata fields. This week we will put those concepts into practice.

The centerpiece of class will be a **structured peer review**. You will exchange MAP drafts and test whether another person can understand and apply the rules you have written. Rather than submitting a draft for detailed instructor grading and then submitting the same assignment again, you will use peer review, hands-on testing, and instructor consultation to identify problems before completing the graded final version.

A good application profile is not simply a table of fields. It is documentation that should allow different people to describe collection items consistently. The best way to evaluate it is therefore to have someone else try to use it.

## Weekly Learning Objectives

By the end of this week, you should be able to:

- *evaluate* a metadata application profile for clarity, completeness, consistency, and usability.
- *apply* another person's MAP to sample collection objects and identify ambiguous or incomplete instructions.
- *provide* specific, constructive peer feedback on metadata design decisions.
- *revise* definitions, obligation, cardinality, controlled vocabularies, encoding schemes, and content guidelines in response to testing and feedback.
- *evaluate* whether a MAP includes the metadata necessary for both resource description and CollectionBuilder functionality.
- *identify* project-specific metadata problems that require additional research or local decisions.
- *develop* a clear revision plan for the final Metadata Application Profile.

## Tasks

### 1. Bring a substantive MAP draft

Bring your current Metadata Application Profile in a form that another student can read and annotate.

Your draft should include, at minimum, your proposed:

- metadata elements/fields;
- definitions;
- obligation;
- cardinality/repeatability;
- controlled vocabularies, where applicable;
- encoding schemes or value standards, where applicable;
- content guidelines;
- example values;
- CollectionBuilder-specific fields needed by your project.

This is a **working draft for peer review, not a graded draft submission**. It does not need to be polished, but it does need to be complete enough for someone else to test.

### 2. Bring sample collection objects

Bring information about **2–3 representative objects** from your proposed collection. Choose objects that will help test your metadata design. If possible, include at least one object that presents a complication or edge case.

# In Class

## Opening Review

We will briefly review the major components of a MAP and discuss common problems that arise when translating general metadata principles into collection-specific rules.

Topics may include:

- unclear or overlapping element definitions;
- fields that are too broad or too narrow;
- inconsistent obligation or cardinality decisions;
- uncontrolled values that would benefit from a vocabulary;
- controlled vocabularies that do not actually fit the collection;
- ambiguous date, name, title, or subject practices;
- missing CollectionBuilder fields;
- rules that make sense to the author but are not clear to another metadata creator.

## Structured Peer Review

You will exchange your MAP with a classmate. Peer review will focus on **using and testing** the profile rather than simply proofreading it.

### Part 1: Read the MAP as documentation

Without an explanation from the author, review the profile and identify:

- fields whose purpose is unclear;
- definitions that could be interpreted in more than one way;
- missing obligation or cardinality information;
- value rules that are incomplete or inconsistent;
- places where examples would help.

### Part 2: Test the MAP

Use your partner's MAP to describe one or more sample objects.

As you work, record places where you have to ask questions such as:

- Which field should contain this information?
- Is this field required?
- Can I enter more than one value?
- Which term should I use?
- What format should this date/name/identifier take?
- Should I transcribe what appears on the object or normalize it?
- What should I do when the information is unknown?

Those questions reveal places where the application profile may need stronger documentation.

### Part 3: Peer feedback

Provide your partner with specific feedback addressing:

1. **What is already clear and usable?**
2. **What was difficult or ambiguous when you tried to apply the MAP?**
3. **What important metadata seems to be missing?**
4. **Which rules need clarification or examples?**
5. **What are the highest-priority revisions before submission?**

The author should then have an opportunity to explain decisions and ask follow-up questions.

## Revision and Project Consultation

Use the remainder of the studio to revise your MAP and work on project-specific metadata questions.

Possible work includes:

- revising element definitions;
- changing obligation or cardinality;
- selecting or replacing controlled vocabularies;
- developing local controlled vocabularies;
- clarifying content guidelines;
- testing date or name conventions;
- checking CollectionBuilder requirements;
- creating sample metadata records;
- consulting with the instructor or AI about unusual collection materials or metadata problems.

## Before You Leave

Create a short revision plan identifying the most important changes you need to make before submitting the final Metadata Application Profile.

The final MAP will be graded **once**, after you have had the opportunity to revise it using peer feedback and testing from today's studio.
