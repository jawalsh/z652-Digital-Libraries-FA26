# Metadata Application Profile (MAP) Peer Review

## Purpose

The goal of this peer review is to **test your partner's Metadata Application Profile (MAP) as working documentation**.

A MAP should allow someone other than its author to create metadata consistently. Your job is therefore not simply to proofread the MAP or decide whether you like its design. Instead, you will try to **use it**.

Pay particular attention to moments when you are unsure what to do. Those moments often reveal where definitions, rules, or examples need clarification.

---

## Part 1: Read the MAP as Documentation

**Do not ask the author to explain the MAP yet.**

Read through your partner's MAP as though you had been given it and asked to create metadata for the collection.

As you read, comment or make notes directly on the MAP.

### Project Introduction

Before looking closely at the individual metadata elements, consider whether you understand the collection itself.

Can you determine:

- what the collection or project is?
- what kinds of materials it contains?
- its general content and scope?
- who its intended or likely users are?
- how users might find, browse, understand, or use the materials?
- the purpose or goals of the project?

Ask yourself:

**Do I understand the collection well enough to understand why these metadata choices were made?**

Note any context that seems necessary for understanding the MAP but is missing or unclear.

### Elements and Definitions

Consider:

- Is the purpose of each element clear?
- Are any elements difficult to distinguish from one another?
- Are any definitions ambiguous?
- Are there elements that seem unnecessary?
- Does important information about the collection seem to be missing?

Check that the MAP includes:

- all required CollectionBuilder-GH elements;
- at least **two visualization elements**;
- one or more relevant **optional fields**;
- at least one **custom metadata field**, with a clear justification.

### Element Documentation

For each element, check whether the MAP provides:

- obligation;
- cardinality;
- content guidelines;
- controlled vocabulary, where applicable;
- syntax encoding scheme or value standard, where applicable;
- Dublin Core mapping;
- illustrative example(s);
- notes, where relevant.

You do not need to evaluate every row with equal attention. Concentrate especially on places where the documentation seems incomplete, unclear, or difficult to apply.

### Obligation and Cardinality

For each element, can you determine:

- whether it is **required, recommended, or optional**?
- whether it may occur **once or multiple times**?

Consider what would happen when:

- required information is unknown;
- an object has multiple creators, subjects, dates, etc.

### Values and Content Guidelines

Can you determine:

- what kind of value belongs in each field?
- whether values are free text or controlled?
- which controlled vocabulary to use, when applicable?
- which encoding scheme or value standard to use, when applicable?
- how names should be entered?
- how dates should be entered?
- how multiple values should be entered?
- whether information should be transcribed from the object or normalized?
- what to do when information is unknown?

Where the MAP identifies a controlled vocabulary, encoding scheme, or other external standard:

- Is a link provided?
- Does the link work?
- Does the linked resource actually help you determine how to create the value?

### Dublin Core Mapping

Check the Dublin Core mappings.

Consider:

- Is a Dublin Core mapping provided for each element?
- Does the mapping make sense based on the definition and intended use of the local element?
- Are there custom elements for which the mapping seems unclear or questionable?

Flag mappings that you think the author should reconsider or investigate.

### Examples

Consider:

- Are examples provided where they would be useful?
- Do the examples follow the stated content guidelines?
- Do the examples actually clarify the rules?
- Are there places where an additional example would eliminate ambiguity?

**Mark anything that makes you think:**

> "I'm not sure what I'm supposed to do here."

Do not resolve these questions with the author yet. **The questions themselves are useful evidence about the MAP.**

---

## Part 2: Test the MAP

Choose at least **one representative collection object** supplied by your partner.

Using only the instructions in the MAP, try to create a metadata record for that object.

If time permits, test a second object, especially an unusual or difficult **edge case**.

### As You Work

Record every place where you have to stop and ask yourself a question such as:

- Which field should contain this information?
- Is this field required?
- Can I enter more than one value?
- What term should I use?
- Where can I find the permitted values?
- What format should this name take?
- What format should this date take?
- Should I transcribe what appears on the object or normalize it?
- What should I enter if the information is unknown?
- Does this information belong in more than one field?
- How should multiple values be recorded?
- Does the MAP tell me enough to make this decision consistently?

**Do not guess silently.** If the MAP does not give you enough information to make a confident decision, note the problem.

As you test the MAP, also consider the relationship between the metadata and the collection:

- Do the selected elements adequately describe this object?
- Is there important information about the object that has nowhere to go?
- Are there fields that do not seem useful for these materials?
- Do the metadata choices support the project's intended users and goals?
- Could another person make the same metadata decisions you just made using these instructions?

---

## Part 3: Discuss Your Findings

You may now talk with the author about the MAP.

Start by explaining your experience **before the author explains their intentions**.

Discuss the following questions:

1. **What is already clear and usable?**
2. **What was difficult or ambiguous when you tried to apply the MAP?**
3. **What important metadata, if any, seems to be missing?**
4. **Which definitions, rules, mappings, or examples need clarification?**
5. **Do the metadata choices make sense for the collection's content, users, and goals?**
6. **What are the highest-priority revisions before submission?**

The author should then explain their decisions, respond to the feedback, and ask questions.

### Important

If the author says something like:

> "What I meant was..."

or

> "For my collection, you're supposed to..."

ask:

> **Does the MAP itself tell me that?**

A verbal explanation may solve the immediate problem, but it may also reveal information that needs to be added to the MAP.

Focus on changes that would make the MAP more complete, consistent, and usable—not minor proofreading or formatting issues.

## Final Question

After testing the MAP, answer this question:

> **Could another person use this MAP to describe similar collection objects consistently without needing the author there to explain the rules?**

If not, identify the most important thing that would make the MAP more usable.
